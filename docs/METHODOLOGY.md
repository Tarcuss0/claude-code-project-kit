# Методология проектов

Правила, которые переносим из проекта в проект. Ядро для Claude Code лежит в CLAUDE.md, здесь объяснения и порядок действий.

## 1. Старт проекта (чек-лист первого дня)

1. Завести репозиторий, сразу положить `.gitignore` и `scripts/check_secrets.py`.
2. Скопировать `CLAUDE.md`, шаблоны `HANDOVER-X.md` и `TESTS-FAILING-X.md`.
3. Заполнить `scripts/project.conf` (слаг проекта, сервер, пути).
4. Разметить зоны для сессий и записать их в HANDOVER-X.md.
5. Поставить бэкап базы на сервере и бэкап на ПК (раздел 5). Проверить восстановление до первого релиза.
6. Положить в репозиторий `docs/schema.sql` как каноничную схему.

## 2. Сессии

- 3–4 сессии, у каждой своя буква и зона: каталоги, тесты, суффикс тестовой БД.
- Ядро и публичный интерфейс ведёт одна сессия. Остальные импортируют только публичное. `tests/test_boundaries.py` сторожит границу.
- Передача состояния только файлами: `HANDOVER-X.md` лежит в репозитории. После сжатия контекста сессия читает его первым.
- Сессия не пушит, не деплоит, на прод не ходит.
- Координация между сессиями идёт через ассистента в чате: он отслеживает связки (кому что нужно после чьей задачи) и напоминает о следующем шаге.

## 3. Цикл задачи

1. Разбор без кода: что происходит, на что влияет, какие риски.
2. План, подтверждение, код.
3. Отчёт сессии: сделано, тесты, хеш, нерешённое, пределы решения.
4. Проверка на живых данных: SQL-запрос, вывод команды. «Тесты прошли» живой проверки не заменяет.
5. Класс найденной ошибки записывается в «свод» в CLAUDE.md.

Дорогие или спорные операции (например, разбор звонка через LLM) запускаются кнопкой, а не автоматом. Повторный запуск любой операции безопасен: ничего не делает второй раз.

## 4. Тесты

- Сессия гоняет тесты своей зоны и затронутых файлов.
- Полный набор в деплой не вшивается: слишком долго ждать. Запускается вручную, когда решаю я (аудит, крупная перестройка). В `deploy.ps1` он есть только как необязательный ключ `-WithTests`.
- Ускорение прогона. Порядок такой:
  1. `pytest --durations=30`: найти, на что уходит время.
  2. Поддельные часы вместо реальных ожиданий.
  3. Маркер `slow` и запуск быстрых тестов отдельно.
  4. `pytest-xdist` (`-n auto`) с отдельной БД на каждый воркер.
  Цель не «быстрее любой ценой»: нестабильные прогоны хуже медленных. Пример из практики: на одном проекте полный прогон сократился с 27 до 6–11 минут.
- Периодический аудит (раз в 1–2 недели или перед крупной перестройкой): полный прогон; каждое падение относим к категории (сломан код / сломан тест / нестабилен); список пропущенных тестов с причинами; поиск тестов-пустышек; сверка `tests/factories.py` с текущими моделями.
- Тесты-пустышки: фабрика задаёт поле, которого нет в схеме; ассерт на пустой коллекции или `None`; исключение поймано и проглочено; проверка молча пропускается без переменной окружения.

## 5. Бэкапы

Всё, что нельзя восстановить, имеет копию вне сервера и вне того диска, где лежит оригинал.

На сервере (`scripts/db-backup.sh`, cron, например 03:30):
- Снимок это каталог `db/daily/<yyyymmdd-HHMMSS>/` с `database.dump` и отметкой `OK`. Дамп пишется в скрытый `.part`, проверяется (`pg_restore --list`), получает `OK` и только потом переименовывается. Видимый каталог всегда целый.
- 7 суточных и 4 недельных снимка, ротация по имени каталога.
- Метка `last-dump.json` после успешного дампа. Её возраст показывает `/status`, при превышении порога (26 часов) приходит тревога.
- Если база общая с другими данными, дамп снимается по схемам (`-n`), восстановление тоже.
- Перед боевой миграцией ручной дамп `<проект>-before-<миграция>.dump`.

На ПК (папка `<LOCAL_BACKUP_ROOT>\<проект>\`, корень задаётся в `project.conf`, создаётся скриптом при первом запуске):
- `db\` снимки с сервера, `repo\` git bundle репозиториев, `state\` метки и логи.
- `scripts/pull-backup.ps1` забирает свежий снимок: один вызов ssh возвращает имя каталога и SHA256 всех файлов; скачивание идёт во временный `.incoming`; после сверки сумм пофайлово (нет файла, сумма другая, лишний файл) каталог переносится на место. Оборванная закачка в хранилище не видна.
- Забираются только снимки с `OK`. Если снимок старше `STALE_HOURS`, скрипт всё равно его забирает, но завершается кодом 2: сервер перестал делать новые, и «успешно подтвердили старое» было бы ложным успехом.
- Чистка локальных снимков по возрасту (по имени каталога, не по времени файла) трогает только свои каталоги (имя и `database.dump` внутри) и не удаляет последние `KEEP_AT_LEAST` снимков при любом возрасте: после двух месяцев простоя ПК не должен стереть единственную копию.
- `scripts/bundle-repos.ps1` делает `git bundle` с проверкой `git bundle verify`, чистит последние `KEEP_BUNDLES`.
- Оба скрипта запускает планировщик Windows раз в 2 часа (`install-backup-task.ps1`), пропущенный запуск догоняется. Коды выхода: 0 всё хорошо, 1 ошибка, 2 снимок просрочен. Ключ сервера обязан лежать в ssh-агенте, иначе `BatchMode=yes` откажет без вопроса.
- Метка `last-pull.json` пишется в `state\` и отправляется на сервер, чтобы `/status` видел свежесть копии на ПК.
- Файлы вроде аудио забираются тем же приёмом (список с суммами, временный каталог, сверка, перенос). Готового скрипта для них в наборе нет.

Бэкап, который ни разу не разворачивали, бэкапом не считается. Проверка восстановления на локальной базе делается до передачи проекта.

Грабли:
- Скрипты PowerShell с кириллицей сохранять как UTF-8 with BOM, а файлы-метки, которые читает Python, как UTF-8 без BOM.
- В Windows PowerShell 5.1 запись нативной команды в stderr при `$ErrorActionPreference = 'Stop'` становится ошибкой, хотя команда отработала. Нативные вызовы идут через `Invoke-Native`, успех решает код возврата.
- `scp` получает точку назначения `.`, а не путь: так в аргументах нет кириллицы и буквы диска с двоеточием, которую `scp` принял бы за имя хоста.
- Пароль со знаком `%` ломает `psql` и `pg_dump` при передаче через URI. Параметры соединения разбираем из `DATABASE_URL` без декодирования (`dburl.py`).
- Команда для ssh в одинарных кавычках без вложенных: PowerShell 5.1 теряет вложенные кавычки при передаче в `ssh.exe`.
- Перед правкой конфигов на сервере делается `.bak`. Если потом нужен откат, список изменений известен.

## 6. Репозиторий

- `.gitignore` в первый день: `.env`, `state.json`, выгрузки, дампы, файлы сессий.
- `scripts/check_secrets.py` перед каждым пушем.
- `git bundle` раз в сутки в `<LOCAL_BACKUP_ROOT>\<проект>\repo\` (защита от потери диска и от переписанной истории).
- Старые исходники при переписывании проекта кладём в `_old/` только для чтения.
- Для второго GitHub-аккаунта отдельный SSH-алиас, чтобы пуш не ушёл не в тот аккаунт.
- Перед тем как приписывать код себе, проверить происхождение: `.git/logs/HEAD` и `.git/config`.
- Закрытый коммерческий код остаётся в приватных репозиториях. Публичные содержат то, что можно показать: README, тесты, CI.

## 7. Деплой (всегда руками)

Порядок:
1. `git status` (дерево чистое, все сессии закоммитили)
2. `git log --oneline` (что уходит)
3. `git diff --name-status` по каталогам миграций
4. Дамп перед миграцией
5. `git push`
6. `.\scripts\deploy.ps1`: проверка секретов, миграции, перезапуск, healthz, откат по хешу при сбое (полный набор тестов только с ключом `-WithTests`)
7. Проверка версии миграций (`alembic_version`)

`-Force` без явной причины не используется. Выкатка одним заходом, когда готовы все сессии. Миграции аддитивные; отметки по старым записям проставляются задним числом, иначе первый запуск разошлёт уведомления по всей истории.

## 8. Сервер

- Каждый шаг с сервером начинается с `ssh`: сессия на сервере после работы закрывается.
- Одна команда на строку, под PowerShell.
- Перед установкой нового сервиса: `ss -tlnp` (порт свободен), `dig +short <домен>` (DNS на месте).
- Шаблон выкладки: systemd + nginx + certbot, доступ закрыт basic auth, пока не нужен публичный.
- Секреты при выводе маскируются: `sed -E 's#://[^@]*@#://***@#'`. Копии `.env.bak` с токенами удаляются.
- В боте или панели команда `/status`: очереди, воркер, место на диске, возраст бэкапов, прогоны в работе.
- Тишина тоже сбой: метка живости (heartbeat) и тревога, если давно нет событий. Предел решения записывается честно (метка ловит упавший процесс, но не зависший).

## 9. Передача проекта

- Руководство простым языком, без ИТ-терминов: как устроено, кто за что отвечает, что делать при сбое.
- Раздел про восстановление пишется так, чтобы переносился в руководство целиком.
- Перед передачей: гигиена сервера (убрать `.env.bak`, дубли строк в `.env`), проверка восстановления бэкапа, список решений за заказчиком.

## Непроверенное записывается в файл

Всё, что не прошло проверку вживую, фиксируется в `docs/KNOWN-GAPS.md`: что именно, почему не проверено и как проверить. Строка уходит из раздела «Не проверено» только после настоящего запуска, с датой и условиями. То же правило действует для отчётов сессий: «не проверено вживую» пишется прямо.
