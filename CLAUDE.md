# CLAUDE.md

Постоянные правила проекта. Читай в начале каждой сессии вместе со своим HANDOVER-X.md.

## Как работаем

1. Сначала разбор, потом код. Перед правками прочитай затронутые файлы целиком и объясни, что меняешь, какие файлы заденешь и какие есть риски. Код пиши после моего подтверждения.
2. Делай только то, что просили. Соседнее не рефактори и не чини, даже если видно, что там плохо. Найденное записывай в свой файл docs/TESTS-FAILING-X.md отдельным разделом.
3. Перед правкой файла проверь через grep, кто его импортирует.
4. Работай только в своей зоне (см. HANDOVER-X.md). Чужие незакоммиченные файлы не трогай, в чужие файлы не пиши.
5. Ядро (`app/core`, `app.core.public`) меняет только сессия А. Остальные пользуются публичным интерфейсом. Границы проверяет `tests/test_boundaries.py`.
6. Стек зафиксирован (версии записаны в `docs/ARCHITECTURE.md`). Новую зависимость, замену библиотеки или фреймворка сам не вводи, даже если так задача решается проще: сначала скажи, зачем, какие есть варианты, и жди моего согласия.
7. Решение, которое трудно отменить (схема данных, способ входа, внешний сервис, порядок выкатки), записывай отдельным файлом `docs/adr/NNNN-имя.md` по шаблону `docs/ADR-TEMPLATE.md`.
8. Задача не закрыта, пока документы не обновлены: если изменились границы компонентов, зависимости, модель данных или состояния объектов, правь `docs/ARCHITECTURE.md` в том же коммите. Это проверяет сторож `scripts/guards/20-docs-sync.py`: менялись миграции или зависимости, а документ нет — выкатка встанет. Если после разбора менять документ не нужно, допиши в тело коммита строку `Архитектура: без изменений`.

## Git

- Коммит только так: `python scripts/commit.py --session X -m "..." <файлы поимённо>`. Внутри `git commit --only`: файлы берутся с диска, чужое из общего индекса не уезжает, при гонке с другой сессией повтор на новом HEAD, после записи сверка состава. Строку `Сессия: X` скрипт допишет сам.
- Нельзя: `git add` с обычным `git commit`, `git commit -a`, ручной `GIT_INDEX_FILE`, `commit-tree` без выравнивания общего индекса, каталоги и маски вместо файлов. Если скрипт напечатал ПЛОХО, не исправляй сам, покажи мне.
- Не делай `git push` и не запускай деплой. Это делаю я сам, руками.
- Копию файла для сравнения бери через `git show HEAD:<путь>`, не из рабочего дерева.
- Не коммить `.env`, дампы, выгрузки, файлы сессий, токены. Перед коммитом: `python scripts/check_secrets.py`.

## Тесты

- Гоняй только тесты своей зоны и затронутых файлов: `pytest -q путь/к/тестам`.
- Если менял ядро или публичный интерфейс, добавь `tests/test_boundaries.py` и тесты модулей, которые импортируют изменённое.
- Полный набор тестов не гоняй и в `deploy.ps1` его не вшивай. Полный прогон запускаю я сам, когда решу (например, при аудите).
- Падающие тесты веди в `docs/TESTS-FAILING-X.md` (X — твоя буква). Файл только твой. Починила — убери строку в том же коммите.
- Исход прогона называй только по `python scripts/outcome.py run -- <пути>`: ЗЕЛЁНЫЙ, НЕ ПРОШЛА, НЕ СОСТОЯЛАСЬ, НЕ ДОШЁЛ. Свой разбор вывода pytest не пиши, код выхода pytest не довод. «Прошли, но 2 ошибки» не зелёный.
- Новый тест проверяй подлогом: убери фикс и запусти `python scripts/outcome.py run --expect-red <тест> -- <файл>`. Подлог ломает сам предмет при той же версии окружения. Откат миграции, остановленная база и другой отказ окружения дают «не состоялась», это не краснота.
- Мера, которая может промолчать по причине окружения (нет базы, нет маркера), печатает своё молчание строкой «НЕ СОСТОЯЛАСЬ» (у сторожа код 3), а не «ок». Проверка называется тем, что измеряет («список пуст: 0 строк по условию X»), а не догадкой о причине («сломан отбор»).
- Не пиши тесты, которые проверяют собственные константы модуля, и ассерты на пустой коллекции.
- У каждой сессии свой комплект (тестовая БД, контейнеры, стенд), у четвёртой тоже. Суффикс и комплект записаны в HANDOVER-X.md, их сверяет сторож `30-session-kits.py`. В чужой комплект не ходи.
- Прогон в комплекте (тесты с базой, сборка стенда) только под замком: `python scripts/run-lock.py <комплект> --session X -- <команда>`. Занят: жди (`--wait`) или бери свой, замок не обходи.
- Замер на стенде огораживай меткой: при сборке `python scripts/stand-mark.py stamp <каталог-сборки> --session X`, замер `python scripts/stand-mark.py around <url-метки> @<каталог-сборки>/stand-mark.txt -- <команда>`. «Не начат» и «не состоялся» не краснота: стенд сейчас не твой.
- Чужой комплект не поднимай и не пересоздавай, даже для проверки «не задел ли я соседа»: подъём применит всё, что накопилось с создания контейнера. Сверяй конфиг чужого сервиса по HEAD против правленого файла и `docker compose up --dry-run` по чужим профилям.

## Сервер и прод

- На прод и сервер не ходи. Команды для сервера готовь мне: одна команда на строку, каждый шаг начинается с `ssh`.
- `scripts/deploy.ps1`, `scripts/lib-deploy.ps1`, `server/release.sh` и сторожей в `scripts/guards/` без моего прямого указания не правь: они стоят между правкой и продом.
- Секреты в ответах маскируй (пароль, токены, ключи). Полные значения не выводи. В команде для сервера секрет не пиши в аргументах и в URL, и не проси вывести его целиком (`grep TOKEN .env` кладёт токен в историю чата).
- Не добавляй в `.claude/settings.local.json` разрешения на `ssh`, `scp`, `rsync`, `curl` и `deploy` к проду.
- Для адреса сервиса не оставляй запасного значения в коде (`?? http://localhost`): нет переменной, значит падай громко.
- Правила безопасности сервера и выкатки: `docs/SECURITY.md`.
- Миграции только аддитивные и обратимые. Перед боевой миграцией я снимаю дамп `<проект>-before-<миграция>.dump`.
- Чистка боевой базы только по `docs/PROD-CLEANUP.md`: транзакцию по каркасу готовишь и гоняешь с подлогами на копии, на бою запускаю я.

## Отчёт в конце задачи

Не пересказывай каждую правку: важное для будущей сессии лежит в документах, а не в этом отчёте. Если что-то не проверено вживую, так и пиши.

## Свод ошибок проекта

Сюда каждая сессия в ту же смену записывает класс ошибки, который нашла: мера отвечала честно, но не на тот вопрос. Одна строка: что случилось и как не повторить.

- Тест проверял константы собственного модуля вместо поведения.
- Копия файла взята из рабочего дерева, а не из `git show HEAD:<путь>`.
- Маска glob зацепила соседние файлы.
- `--down` без суффикса набора снёс чужой стенд.
- Фабрика патчила поле, которого нет в схеме, pydantic молча его отбросил, тест перестал что-либо проверять.
- Зонд назвал зелёным «12 прошли, 2 ошибки», другой не узнал упавших и доложил, что подлог не покраснел: исход называет только `outcome.py`.
- Сторож полгода молчал: базы с историей миграций не было, а молчание печаталось как «ок». Мимо проехали шесть пропаж парной правки схемы.
- Сторож краснел словами «сломан отбор», а пустой список был правдой: два дня искали дефект, которого нет.
- Подлог откатом миграции дал отказ окружения, его приняли за красноту.
- Обычный `git commit` одной сессии увёз подготовленные пути другой; вчерашний `git add` увёз вчерашнюю версию вместо сегодняшней.
- Подъём чужого комплекта для проверки «не задел ли я соседа» пересоздал контейнер, два месяца живший со старой настройкой: чужое накопленное показалось своим.
- Метка `com.docker.compose.config-hash` на живом контейнере не совпадает с `config --hash` даже у свежего: мера назвала бы отставшими все сервисы.
- Погашенные отметкой строки файлов ссылались на удалённого владельца: сторож сирот без условия «живые строки» назвал их новыми сиротами.
