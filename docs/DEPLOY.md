# Выкатка

Выкатку запускает человек, руками, после `git push`. Сессии Claude Code её не запускают. Скрипт один на все артефакты проекта (бэкенд, фронт, что угодно ещё), порядок и команды сборки берёт из `scripts/project.conf`.

Что проверено на поддельном сервере и что нет: `docs/KNOWN-GAPS.md`. Первый боевой запуск начинай с `-WhatIf`.

## Запуск

```
.\scripts\deploy.ps1 -WhatIf
```

```
.\scripts\deploy.ps1
```

| Ключ | Что делает |
|------|------------|
| без ключей | выкатывает все артефакты из `DEPLOY_ARTIFACTS`, по порядку |
| `-Only backend` | только названные; порядок остаётся из настроек |
| `-WhatIf` | печатает план и гоняет настоящие проверки дерева, на сервер не ходит |
| `-Force` | выкатить грязное или разошедшееся с origin дерево. Не «отключить проверки», а «вижу и беру на себя»: список файлов печатается всё равно, а в итоге остаётся красная пометка |
| `-MarkOnly` | ничего не выкатывать, записать маркер по факту (только для артефактов, чья версия на сервере равна HEAD дерева) |
| `-Rollback backend` | вернуть артефакт на прежний релиз, маркер пишется по тому, что назвал сервер |
| `-WithTests` | перед выкаткой полный набор тестов (`TEST_CMD`). По умолчанию выключен |
| `-Server` | другой адрес вместо `SERVER_HOST`, пока DNS смотрит в сторону |

Вопросов скрипт не задаёт: запуск годится для удалённого вызова. Каждый запуск пишет свой журнал `.deploy-logs/deploy-<время>.log`, путь печатается в начале и в конце: упавший посередине скрипт до конца не доходит, а журнал к тому моменту уже есть. Итог идёт коротким блоком в конце: выкачено или отказ, версия, релиз, путь к журналу.

## Что делает скрипт

1. **Проверки дерева.** Дерево чистое, совпадает с origin (состояния «впереди», «позади», «разошлось», «нет upstream», «нет связи» различаются), сторожа (`scripts/checks.py`), `PRE_DEPLOY_CMD`, при `-WithTests` ещё и `TEST_CMD`. Хоть одна красная: выкатка не начинается, прод не тронут.
2. **По артефактам, в порядке `DEPLOY_ARTIFACTS`:** сборка на ПК (`BUILD_CMD`) в `STAGE_DIR`, штамп `version.json`, упаковка в `<артефакт>-<время>.tgz`, `scp` в `<REMOTE_DIR>/incoming`, `ssh <приёмник> receive <архив>`.
3. **Приём на сервере** (`server/release.sh`): распаковка в новый каталог релиза, `PRE_SWITCH_CMD` (миграции), переключение симлинка `current`, `RESTART_CMD`, ожидание здоровья. Не поднялось: симлинк возвращается на прежний релиз, сервис перезапускается, неудачный релиз остаётся с суффиксом `.failed` для разбора.
4. **Сверка.** После каждого артефакта скрипт спрашивает у сервера его версию и сравнивает с деревом. «НА СЕРВЕРЕ ДРУГОЙ КОММИТ» значит, что симлинк остался на прежнем релизе, хотя ошибок не было. Сверка предупреждает, но выкатку не роняет.
5. **Маркер** `deploy/deployed.json` записывается по тому, что приняли серверы, коммитится, пуш идёт попыткой.
6. **Серверный `release.sh`** обновляется следом, после успеха (см. ниже).

Повторный запуск безопасен: каждый релиз лежит в своём каталоге, симлинк переключается последним и только после успешной проверки.

## Порядок артефактов

Правило одно: **схема впереди кода, бэкенд впереди фронта.** Пиши в `DEPLOY_ARTIFACTS` именно так: `backend,frontend`.

Фронт при серверной отрисовке ходит в API на каждой странице. Выкатишь его первым: он пойдёт в старый бэкенд и получит 404 на новых полях. Обратный порядок безопаснее, потому что новый бэкенд обязан уметь обслуживать и старый фронт. Это гарантирует правило аддитивных миграций ниже.

Миграции идут отдельным шагом до подъёма сервиса (`PRE_SWITCH_CMD`). Не прошла миграция: симлинк не переключён, прод на прежнем релизе.

## Один артефакт, один пользователь

У каждого артефакта свой пользователь ssh и свой каталог (`<имя>.SSH_USER`, `<имя>.REMOTE_DIR`). Не выдавай пользователю фронта группу `docker` и `sudo`: это равносильно root и сводит на нет всё разделение. Приёмник, которому нужен root (docker), запускай под root, а скрипты, которые зовёт root, держи там, где обычный пользователь писать не может (`/usr/local/sbin`, `/usr/local/bin`).

## Правило миграций: только аддитивные, в три выкатки

Откат переключает **код**. Базу он не трогает и не может: откатить `DROP COLUMN` нечем. Поэтому схема всегда совместима и со старым кодом, и с новым.

Переименование колонки `a` в `b` делается за три релиза:

| Релиз | Миграция | Код |
|-------|----------|-----|
| 1 | `ADD COLUMN b`, заполнить из `a` | про `b` ещё не знает |
| 2 | нет | пишет в `a` и `b`, читает `b` |
| 3 | `DROP COLUMN a` | про `a` уже забыл |

Между релизами должно пройти достаточно времени, чтобы стало ясно: откат не понадобится. Практически хотя бы сутки на проде.

Никогда: `DROP COLUMN` или `RENAME` в одном релизе с кодом, который на них рассчитывает; `SET NOT NULL` без заполнения и проверки; миграции с долгой блокировкой на работающей базе. После ручного отката скрипт напоминает: «Схема базы осталась новой».

## Сторожа дерева

`python scripts/checks.py` запускает проверку секретов (`check_secrets.py`, всегда первой) и все файлы `scripts/guards/*.py` по порядку имён. Образец: `scripts/guards/_template.py`; файлы с `_` в начале не запускаются.

Шапка сторожа (первые 15 строк):

```
# about: что стережёт (печатается в отчёте)
# needs-db
# cwd: frontend/src
```

`needs-db` означает «нужна поднятая база», такого сторожа пропускает `--quick`. `cwd` задаёт каталог запуска относительно корня. Контракт: код 0, если всё хорошо; иначе 1 и строки с «ПЛОХО» или «ОТКАЗ», именно они попадут в отчёт, а не хвост вывода.

**Почему не хук.** Хук локален, снимается ключом `--no-verify`, не приезжает с репозиторием и у трёх сессий будет в трёх состояниях. Через выкатку проходит всё, обойти её нельзя. Мера, которую никто не зовёт, неотличима от работающей: сторож, не подключённый к выкатке, не стережёт.

Что в сторожа не идёт: проверки, которым нужен поднятый стенд (рендер, скриншоты). Им место в ручном прогоне перед выкаткой.

## Что на проде сейчас: маркер

```
python scripts/deployed.py
```

Печатает, какой коммит и релиз стоят на каждом артефакте и что из дерева ещё не уехало. `--short` даёт одну строку для отчёта.

Маркер `deploy/deployed.json` пишет сама выкатка в момент успеха и тут же коммитит; пуш идёт попыткой, неудача печатается строкой и выкатку не роняет.

- **Почему не `git log origin/main..HEAD`.** `origin/main` в дереве это снимок последнего `fetch`: после выкатки он устаревает молча, и выкаченные коммиты числятся невыкаченными. Маркер лежит в том же дереве, куда его записала выкатка.
- **Записей по числу артефактов.** Они едут по отдельности, и `-Only` оставляет остальные на прежнем коммите. Невыкаченное считается от **отставшего**: коммит выкачен только тогда, когда он есть во всех.
- **Коммиты самой выкатки не считаются.** Маркер коммитится после выкатки, то есть по определению «не выкачен». Такие коммиты отличаются по составу файлов (тронут только маркер), а не по тексту сообщения: сообщение можно повторить руками, состав нет.
- **Пишется по факту.** Если первый артефакт приняли, а второй нет, в маркер попадает первый. Если сервер откатил релиз сам, маркер остаётся на прежнем коммите.
- **Поле `dirty` читать обязательно.** При грязном дереве коммит совпадает, а содержимое на сервере другое.

## Что именно выкачено: `version.json`

Имя релиза это время выкатки. На вопрос «какой код на сервере» оно не отвечает. Поэтому скрипт кладёт в каждый артефакт `version.json`:

```json
{
  "component": "backend",
  "release": "20260812-165841",
  "version": "a98f3b6",
  "commit": "a98f3b6...",
  "commit_short": "a98f3b6",
  "branch": "main",
  "dirty": false,
  "dirty_files": 0,
  "built_at": "2026-08-12T16:58:41+03:00"
}
```

Штамп снимается один раз на выкатку, поэтому все артефакты одного запуска несут один коммит. Каталог внутри артефакта задаёт `<имя>.VERSION_DIR`. `dirty: true` это правда о сборке, а не ошибка: на сервер уехал код, которого нет ни в одном коммите.

## Здоровье: два адреса

Рекомендуемое соглашение для сервиса:

| Адрес | Что проверяет | Ответ |
|-------|---------------|-------|
| `/healthz` | процесс жив | `200`, пока процесс отвечает |
| `/health` | процесс жив и **база отвечает** | `200`, иначе `503` |

Выкатка проверяет `/health`: поднявшийся процесс без базы выкаткой не считается. Оба адреса отдают JSON с `version` из `version.json`, то есть с полем `version.commit`. Тело ответа по формату: `{"status": "ok", "version": {"commit": "..."}}`.

Скрипт берёт из ответа JSON между первой `{` и последней `}`, поэтому лишний текст вокруг ему не мешает. Сервис, который не отдаёт версию, ставится на сервер как обычно, но сверки не получит: в итоге будет «не подтверждено». Это предупреждение, а не отказ.

Закрой оба адреса снаружи, если состав внутренних проверок наружу не нужен (`allow 127.0.0.1; deny all;`), и указывай в `<имя>.HEALTH_URL` тот адрес, который виден с ПК, и в `release.env` (`HEALTH_URL`) тот, что виден на самом сервере. Это обычно два разных адреса.

## Серверный приёмник: `server/release.sh`

Один скрипт на все артефакты. Команды: `receive <архив>` и `rollback [<релиз>]`. Настройки лежат в `release.env` рядом с каталогами артефакта (образец: `server/release.env.example`).

Раскладка на сервере:

```
<REMOTE_DIR>/
  release.env       настройки приёма
  incoming/         сюда приходят архивы
  releases/<время>/ релизы
  current -> releases/<время>
```

Что защищено: имя архива проверяется по шаблону, пути с `..` и абсолютные отвергаются, распаковка идёт во временный `.part`, ставится замок (`flock`), чтобы две выкатки не наложились; старые релизы и архивы чистятся, но `KEEP_RELEASES` не меньше 2 и текущий релиз не удаляется ни при каких условиях; ручной откат никогда не выбирает целью `.failed`.

### Первая установка на сервер (один раз, руками)

Выкатка не может положить приёмник сама: она его вызывает. Один раз создай на сервере каталоги и установи скрипт. Каждая строка отдельно, шаги начинаются с `ssh`:

```
ssh root@<сервер> mkdir -p <REMOTE_DIR>/incoming
```

```
scp server/release.sh root@<сервер>:/usr/local/bin/release-backend.sh
```

```
ssh root@<сервер> chmod 755 /usr/local/bin/release-backend.sh
```

```
scp server/release.env.example root@<сервер>:<REMOTE_DIR>/release.env
```

```
ssh root@<сервер> nano <REMOTE_DIR>/release.env
```

Для артефакта не под root каталоги принадлежат его пользователю (`chown -R <пользователь> <REMOTE_DIR>`), а `release.env` читает только он. Дальше `release.sh` обновляет сама выкатка (см. следующий раздел).

### Серверные скрипты: их везёт выкатка, но со следующего раза

Приём ставится один раз, и выкатка не обновляла бы его: она вызывает тот файл, что уже лежит на сервере. Правка в репозитории до прода не доезжала бы вовсе. Поэтому `deploy.ps1` довозит `server/release.sh` сам. Три правила, каждое важно.

**Ставится ПОСЛЕ успешной заливки.** Выкатка всегда идёт приёмом, проверенным работой; новый следом. Следствие: **правка приёма вступает в силу со следующей выкатки**. Положенный первым сломанный приём отбирает и заливку, и откат: заменяемый файл и есть тот, которым работаем.

**Неудача доставки не отказ выкатки.** К этому моменту прод обновлён и работает; объявить отказ значило бы сказать неправду о его состоянии. Беды поднимаются строкой в итоговый блок.

**Промежуточный файл для root лежит в `/root`, а не в `/tmp`.** `/tmp` пишут все, и пользователь заранее кладёт туда симлинк на любой файл: `scp` под root идёт по симлинку и пишет от root куда указано. Второй заход: подменить файл между `scp` и `install`, и root сам поставит чужой скрипт. `/root` доступен только root, обе двери закрыты устройством, а не проверкой. Для остальных пользователей файл идёт в `incoming/` их артефакта.

Проверяется содержимое: хеш файла в репозитории сверяется с `sha256sum` на сервере. Отдельно проверяются концы строк: скрипт с CRLF на сервере не запустится вовсе (`bash` не понимает `#!/usr/bin/env bash` с возвратом каретки), такой файл не отправляется и о нём сказано отдельно. Держи `*.sh text eol=lf` в `.gitattributes`.

## Откат

Артефакт откатывается **сам**, если после переключения не прошла проверка здоровья. Руками, после успешной выкатки:

```
.\scripts\deploy.ps1 -Rollback backend
```

Или прямо на сервере:

```
ssh root@<сервер> /usr/local/bin/release-backend.sh --root <REMOTE_DIR> rollback
```

Откат возвращает код. Схема базы остаётся новой, ради этого и существует правило аддитивных миграций.

## Что сделать заранее

Эти шаги в скрипт не входят. Первые три обязательны для удалённого запуска: без них выкатка встанет посреди процесса и будет ждать человека у терминала, которого рядом нет.

| Шаг | Зачем |
|-----|-------|
| `ssh <пользователь>@<сервер> true` для каждого пользователя из настроек | принять ключ хоста: незнакомый отпечаток ssh спрашивает с клавиатуры, и скрипт на этом повиснет |
| ключ в агенте Windows OpenSSH (`ssh-add`) | Git Bash и PowerShell используют разные агенты; ключ, добавленный не туда, скрипт не увидит |
| `git push` | скрипт требует совпадения с `origin`, но не пушит сам |
| проверки, которым нужен стенд | необязательно, но перед выкаткой фронта стоит |

## Типичные отказы

| Что видим | Причина |
|-----------|---------|
| «грязное дерево» | незакоммиченные файлы; закоммить или `-Force` |
| «дерево впереди origin» | забыт `git push` |
| «дерево разошлось с origin» | чужой пуш; подтяни и пересобери |
| красный сторож | причина выше в отчёте; сторож не обойти, только исправить |
| «сборка X вернула код N» | упал `BUILD_CMD`; на сервер ничего не залито |
| «здоровье не подтвердилось» | приём откатил релиз сам; смотри `<REMOTE_DIR>/releases/*.failed` и журнал сервиса |
| «НА СЕРВЕРЕ ДРУГОЙ КОММИТ» | симлинк остался на прежнем релизе; разобраться в журнале приёма |
| «не подтверждено» | сервис не отдаёт `version.commit`; выкатка прошла, сверки нет |

## Известные ямы

1. **Автооткат без живой проверки.** На поддельном сервере он проверен, на настоящем нет. Проверка: выкати заведомо неработающую сборку так, чтобы здоровье не ответило, и убедись, что прод вернулся на прежний релиз сам.
2. **Один экземпляр сервиса.** При переключении возможен короткий разрыв. Нужен нулевой простой: две копии за балансировщиком и свой `RESTART_CMD`.
3. **Сборка на машине разработчика.** Тяжёлую сборку (фронт) на маленьком сервере не запускай: уйдёт в нехватку памяти.
4. **Секреты не в артефакте.** Рантайм-секреты лежат на сервере в своём файле и в архив не попадают. Переменные, которые вшиваются в клиентский код на этапе сборки, секретов содержать не должны: всё, что туда попало, уедет в браузер каждому посетителю.
