# Безопасность прода и выкатки

Чек-лист, собранный из разбора настоящего взлома и двух аудитов после него. Это не пентест и не гарантия: список мер, у каждой есть причина и способ проверить вживую. Команды для сервера идут по одной, каждый шаг начинается с `ssh`. Что из этого проверено на настоящем сервере, а что нет: `docs/KNOWN-GAPS.md`.

## Как это случилось (без имён)

Веб-приложение на Node с известной уязвимостью удалённого выполнения кода. Обновление было проверено, но не выкачено: лежало в очереди. Процесс фронта работал под root, и один запрос без входа дал root на машине. За сутки ушли все секреты из общего `.env`, на сервере встали два бэкдора, черви разослали ключ и стали перебирать другие хосты. Сервер не чистили, а пересобрали с нуля.

Отсюда первые два правила, остальное следствия.

1. **Обновление безопасности не ждёт очереди.** Проверенное, но не выкаченное исправление уязвимости это открытая дыра. Такую правку выкатывай вне плана.
2. **Процесс, смотрящий в интернет, никогда не root и не видит чужих секретов.** Дыра в нём не должна давать больше, чем ему положено.

## Сервер

| Мера | Зачем | Проверка |
|------|-------|----------|
| Фронт и бэкенд под разными пользователями без `sudo`, без группы `docker` | группа `docker` равна root | `ssh root@<сервер> id <пользователь-фронта>` |
| Секреты бэкенда в файле `600` владельца root; у фронта свой файл с тем, без чего он не работает | дыра во фронте не отдаёт пароль базы и ключи | `ssh root@<сервер> sudo -u <пользователь-фронта> cat <путь-к-env-бэкенда>` должен отказать |
| `ufw default deny incoming` явной строкой, открыты только 22, 80, 443 | политика по умолчанию берётся из `/etc/default/ufw`, а `enable` её не сбрасывает | `ssh root@<сервер> ufw status verbose` |
| Внутренние порты (база, кэш, хранилище, приложение) слушают только `127.0.0.1` | состояние процессов не равно состоянию файрвола | `ssh root@<сервер> "ss -tlnp"`: на `0.0.0.0` только 22, 80, 443 |
| Порты контейнеров опубликованы как `127.0.0.1:порт:порт` | docker пишет свои правила в обход `ufw` | та же команда `ss -tlnp` |
| SSH: только ключ, `PermitRootLogin prohibit-password`, `PasswordAuthentication no` | пароль перебирают круглосуточно | `ssh root@<сервер> "sshd -T \| grep -iE 'permitrootlogin\|passwordauthentication'"` |
| `fail2ban` с джейлом на ssh и на форму входа приложения | перебор паролей | `ssh root@<сервер> fail2ban-client status` |
| Отдельный `server` в nginx на запросы без имени сайта: `ssl_reject_handshake on` и `return 444` | фоновый шум и черви ходят по IP без имени | с ПК два случая: запрос по IP без имени и запрос с подставленным `Host` |
| Служебные адреса (`/healthz`, `/health`, `/docs`, `/openapi.json`) закрыты снаружи | состав внутренних проверок не нужен чужим | `curl -s -o /dev/null -w "%{http_code}" https://<домен>/healthz` должен дать 404 |
| `server_tokens off`, защитные заголовки на всех ответах, в том числе на 404 | версия nginx в ответе упрощает поиск уязвимости | `curl -sI https://<домен>/нет-такой-страницы` |
| Файлы бэкапов `600`, каталог `700`, `UMask=0077` в юните | один неосторожный `chmod 755` на каталог открывает дампы всем локальным | `ssh root@<сервер> ls -la <каталог-бэкапов>` |

### Порядок правки SSH

Ошибка здесь закрывает вход на сервер, поэтому порядок жёсткий.

1. Проверь, что вход по ключу работает: открой вторую сессию, не закрывая первую.
2. Положи правку отдельным файлом с **малым номером**: `/etc/ssh/sshd_config.d/10-hardening.conf`. `sshd` берёт первое найденное значение, и файл `50-cloud-init.conf` перебьёт настройку из файла с номером 99: она будет выглядеть применённой и ничего не делать.
3. `sshd -t` (проверка синтаксиса), затем `systemctl reload ssh`.
4. Проверь вход ещё одной новой сессией и только потом закрывай старые.
5. Проверь итог: `sshd -T`, а не файл. Реальное значение видно только там.

Каждый сервер получает свой ключ (`ssh-keygen -t ed25519 -f ~/.ssh/<имя>`) и запись в `~/.ssh/config` с `IdentityFile` и `IdentitiesOnly yes`. Комментарий в `config` должен говорить правду: сессия дважды зашла не на тот сервер по алиасу с неверным комментарием.

## Секреты

- **Не в командной строке.** Токен в URL у `curl` виден любому локальному пользователю в `/proc/<pid>/cmdline`. Передавай через `-d`, заголовок или файл.
- **Не в чате.** `grep TOKEN .env` на сервере кладёт токен в историю чата навсегда. Маскируй при выводе: `sed -E 's#=.*#=***#'`. Если секрет всё же попал в чат, перевыпусти его.
- **Не в git.** В `.gitignore`: `.env*`, `*.pem`, `*.key`, `.claude/settings.local.json` (в нём разрешённые сессиям команды, иногда с адресами и токенами), выгрузки с данными клиентов (`*.xlsx`, `*.csv`). Если файл однажды попал в историю, его блоб остаётся там после удаления из дерева: считай, что он утёк.
- **Секреты веб-хуков и сидов** (`WEBHOOK_SECRET`, пароль демо-данных) пустыми не оставляй: пустой секрет принимает любого.
- **Для каждого сервера свой ключ.** Ключи без парольной фразы в `~/.ssh` может прочитать любая сессия с разрешением на чтение домашней папки.

## Выкатка и зависимости

- **Падать громко.** Запасное значение адреса сервиса (`?? http://localhost:8000`) превращает «не подхватился `.env`» в тихую поломку. Хуже всего, если запасное значение в проверке здоровья: сайт не работает, а проверка отвечает «живой». Нет переменной, значит не стартуем.
- **Здоровье проверяет настоящий путь.** `/healthz` отвечает за процесс, `/health` за базу. Если сайт ходит в API на сервере, проверка должна пройти тем же путём (см. `docs/DEPLOY.md`).
- **Перед миграцией дамп**, с проверкой: код выхода, файл есть, размер не ноль, `pg_restore --list` читает его. Не прошёл любой пункт: выкатка останавливается. Тихая деградация («сняли что смогли») хуже отказа.
- **Зависимости**: `npm audit` и `pip-audit` как сторож (`scripts/guards/`), а не раз в год вручную. Читай, что именно уязвимо и достижимо ли оно у тебя (есть ли нужный модуль и путь), но решай по факту, а не по привычке откладывать.
- **Бэкапы наружу шифруй** до отправки, ключ держи не на том же сервере. Дамп это все данные клиентов сразу.

## Сессии Claude Code

- На прод сессии не ходят. Им нужна проверка на сервере: они пишут команду, ты выполняешь и приносишь вывод.
- **Разрешения копятся.** В `.claude/settings.local.json` за месяцы набирается десятки одобрений. Раз в месяц просматривай их, а искать надо по назначению (IP и имя хоста, `ssh`, `scp`, `rsync`, `curl`, `deploy`), а не только по имени: в одном аудите по имени нашлось 48, а ещё 14 ходили на те же машины по адресу.
- **Скомпрометированные адреса** записывай в правила: «этот адрес больше не наш, разрешений на него быть не должно». Следующая сессия видит в истории просто IP и не знает почему.
- **Вложенный `ssh`.** Если уже стоишь на сервере, команду `ssh` из него на тот же сервер не запускай: получишь отказ по ключу и подумаешь, что сломан доступ.

## Если взломали

Не чисть, а пересобирай: черви оставляют закладки, которых не найти.

1. Сделай снимок диска и выключи сервер. Не удаляй: он нужен для разбора.
2. Разбор только на копии, с запретом всего входящего и с диском, смонтированным только на чтение (`mount -o ro,noexec,nosuid,nodev`).
3. Что смотреть: `authorized_keys`, юниты `systemd` в `/usr/lib/systemd/system`, а не только в `/etc/systemd/system` (бэкдоры лежали именно там), cron, `/etc/ld.so.preload`, `dpkg --verify`, `/dev/shm`, журналы nginx и pm2.
4. **Перевыпусти всё, что лежало на сервере:** токены ботов, секреты веб-хуков, ключи хранилищ и бэкапов, ключ подписи сессий (все выйдут из системы, это нормально), пароль базы, SSH-ключи, пароли демо-данных. Содержимое базы считай скомпрометированным.
5. Определи окно взлома (первый и последний подозрительный запрос) и проверь, что выкатки в это время не изменены (время `ctime` файлов).
6. Новый сервер поставь по чек-листу выше.
7. На будущее: `log_connections` в Postgres включён, журналы nginx хранятся не меньше 30 дней (иначе нечем будет доказывать окно).

## Что не проверено

Чек-лист собран из практики и ответов настоящего сервера в прошлых проверках, но каждая команда на новом сервере не прогонялась скриптом из этого набора. Проверь его на своём сервере и отметь результат в `docs/KNOWN-GAPS.md`. В набор пока не вошли: сторож зависимостей (`npm audit`, `pip-audit`) как готовый файл, проверка заголовков как скрипт и ротация журналов под 30 дней.
